# kernel-misra-c

## 适用边界

用于：

- 编写或修改 C 代码。
- 审查 C 补丁、驱动、内核模块或嵌入式应用。
- 需要同时考虑内核风格、MISRA 约束和项目静态分析门禁的场景。

不用于：

- C++、Rust、Python 或纯构建脚本。
- 只调整目录、CI 或工具配置，且不涉及 C 代码语义。

## 规则优先级

按以下顺序执行，后项不得推翻前项：

1. 项目、子系统或板级编码规范。
2. 项目声明的 MISRA C 版本、规则配置、偏差（deviation）和安全约束。
3. Linux 内核 coding style 与 `checkpatch.pl`。
4. 本 skill 的默认建议。

当内核风格与 MISRA 冲突时，**安全约束优先**。例如 MISRA 要求控制流语句带花括号时，使用花括号，即使内核风格倾向省略。若因此偏离内核风格，在提交信息或代码注释中记录原因。

## 开工前确认

- 项目使用的 C 标准：C90、C99、C11 或其他。
- MISRA 版本与配置：MISRA C:2012、MISRA C:2023 或项目自定义规则集。
- 已批准的偏差清单和静态分析工具。
- 当前文件、邻近代码和子系统的既有风格。
- 编译器、格式化、静态分析和测试命令。

项目未指定 MISRA 版本时，可把 MISRA C:2012 的高风险约束作为临时检查基线，但在结果中标记 `[待确认]`，不要声称正式合规。MISRA 版本、规则配置或分析报告缺失时，代码审查只能说明已检查的范围。

## 编写代码的硬要求

- 新代码必须在项目编译选项下无新增警告。
- 接口类型明确；硬件、协议和 ABI 边界使用项目规定的固定宽度类型。
- 变量使用前初始化；结构体和数组不得留下未初始化字段。
- 检查所有可能失败的返回值，覆盖错误路径和资源释放。
- 数组、循环和算术必须有明确边界；防止整数溢出、越界和未定义行为。
- 默认禁止递归和动态内存；项目允许时必须说明生命周期、失败路径和上限。
- 禁止隐式窄化、符号转换和指针/整数互转；必须转换时显式写出并说明理由。
- MISRA 适用时，控制流语句使用花括号；`switch` 覆盖枚举并处理 `default`。
- `volatile` 只用于硬件寄存器或确有外部变化的对象，不能当作锁或内存屏障。
- 共享数据必须遵循项目的锁、原子操作、RCU 或中断上下文规则。
- 宏参数必须加括号，避免重复求值和隐藏副作用；能用 `static inline` 时优先使用。
- 错误码、日志级别、清理顺序和命名遵循所在子系统的既有约定。

## 内核风格要点

- 缩进使用 8 字符 tab；避免超过 80 列。
- K&R 花括号风格；运算符两侧留空格；逗号后留空格。
- 函数和变量使用 snake_case；避免无意义的缩写和匈牙利命名。
- 注释解释为什么，不重复代码表面行为；内核代码优先使用 `/* ... */`。
- 优先复用子系统 API、错误码和清理模式；不要自造并发或内存抽象。
- 内核清理标签 `goto` 很常见，但 MISRA 可能禁止 `goto`；见 `references/conflicts.md`。
- 修改后运行适用的 `checkpatch.pl`，但它不是逻辑正确性或 MISRA 合规证明。

## MISRA 工作方式

- 先按项目配置运行静态分析，再处理报告；不要凭记忆逐条套规则。
- 区分 Mandatory、Required、Advisory 规则和已批准偏差。
- 未定义行为、未初始化对象、越界、无效指针和未检查返回值属于阻塞问题。
- 规则冲突或项目缺少偏差流程时，先标记 `[待确认]`，不要自行豁免。
- 不能仅凭“代码看起来安全”写出“MISRA compliant”。

## 修改与验证流程

1. 阅读目标文件和邻近实现，确认现有风格与错误处理模式。
2. 做最小必要修改，不顺手重排无关代码。
3. 运行项目格式化、编译和静态分析；没有工具时明确说明缺什么。
4. 检查 diff：边界、错误路径、并发、资源释放、类型转换和偏差记录。
5. 报告实际通过的检查；未运行或无法运行的项目写 `[待确认]`。
