# MISRA C 使用要点

## 先确认合规边界

MISRA 不是单纯的代码风格。开始前必须有：

- 使用的 MISRA 版本，例如 MISRA C:2012 或 MISRA C:2023。
- 项目采用的规则集、Amendment 和配置。
- 强制、必需、建议规则的处理方式。
- 已批准偏差（deviation）的编号、范围、理由和审批人。
- 编译器、静态分析工具和报告格式。
- 项目是否需要“合规声明”，还是只把 MISRA 作为缺陷预防清单。

项目未指定版本时，可把 MISRA C:2012 的高风险约束作为临时检查基线，但仍要标记 `[待确认]`。缺少配置或分析报告时，不要仅凭代码阅读声称“MISRA compliant”。

## 规则分类

通常需要区分：

- Mandatory：原则上不允许偏差，必须消除。
- Required：必须遵守；确实不能遵守时走正式偏差流程。
- Advisory：项目可根据风险决定，但仍需记录取舍。

不同 MISRA 版本和工具配置可能改变具体处理方式，以项目规则为准。

## 重点风险区域

### 未定义和未指定行为

- 不读取未初始化对象。
- 不对空指针解引用，不越界访问数组。
- 避免有符号整数溢出、无效移位和未定义求值顺序。
- 避免依赖实现定义的整数宽度、位域布局和类型转换。
- 不把 `memcpy()` 当作任意对象类型的通用转换工具，除非项目允许并满足对齐与别名要求。

### 类型与转换

- 使用项目的 essential type 规则检查隐式转换。
- 禁止无理由的窄化、符号变化和指针/整数互转。
- 显式转换必须证明值域安全，并写清理由。
- 硬件寄存器、协议字段和 ABI 边界使用固定宽度类型。
- 枚举、布尔表达式和位掩码保持类型一致；不要把任意整数直接当布尔值。

### 初始化与对象生命周期

- 所有自动变量、结构体字段和数组元素在使用前初始化。
- 资源申请后立即建立单一所有权和失败清理路径。
- 释放后不继续访问；不重复释放。
- 不使用已离开作用域对象的地址。
- 全局和静态对象的状态转换必须可证明。

### 控制流

- 迭代和选择语句的主体使用复合语句，例如 MISRA C:2012 Rule 15.6。
- `switch` 结构完整；覆盖枚举值并处理 `default`，除非项目规则明确允许其他形式。
- 不写不可达代码；不依赖隐式 fallthrough，除非有明确注释和项目许可。
- 避免复杂条件中的副作用；布尔表达式不应改变程序状态。
- `goto` 通常受 MISRA 限制；内核清理标签需要偏差或重构，见 `conflicts.md`。

### 函数与返回值

- 非 `void` 函数的返回值必须被使用或显式丢弃，并说明原因。
- 函数参数和返回值类型明确；不要依赖旧式隐式声明。
- 默认禁止递归，例如 MISRA C:2012 Rule 17.2。
- 避免函数产生隐藏全局状态变化；所有外部影响应在接口中体现。
- 错误路径必须可枚举，资源释放必须完整。

### 指针与数组

- 指针只在有效对象或数组范围内运算。
- 不越过数组末尾做算术，即使之后不再解引用。
- 不把整数常量随意转换为指针；地址映射必须由项目封装。
- 指针类型转换要满足对齐、别名和对象表示要求。
- 使用 `sizeof` 时避免对指针求数组大小；优先使用项目数组大小宏。

### 内存与标准库

- 默认不使用动态内存；MISRA C:2012 Rule 21.3 限制 `<stdlib.h>` 的分配/释放函数。
- 使用受限标准库函数前检查项目允许列表和错误语义。
- 不依赖 `setjmp()` / `longjmp()`、非标准扩展或未声明的库行为，除非项目明确允许。
- 字符串和缓冲区操作必须有明确长度、终止符和失败处理。

### 预处理与宏

- 宏参数和整个表达式加括号；避免重复求值。
- 不隐藏控制流、资源申请、锁或 `return`。
- 条件编译必须可追踪；不要用宏改变类型语义而不留文档。
- 头文件保护、包含顺序和外部声明遵循项目规则。

### 并发与硬件访问

- 明确共享对象的保护方式：锁、原子操作、RCU、禁用中断或单线程约束。
- `volatile` 不是互斥原语，也不保证原子性或顺序。
- MMIO 使用项目 accessor；不要假设普通 C 读写具有硬件语义。
- 中断上下文、软中断、工作队列和线程上下文的约束必须写清楚。
- 时间、超时和重试循环必须有上界。

## 工具与证据

最低证据通常包括：

- 编译器在项目选项下无新增警告。
- 适用静态分析器的完整报告，以及报告对应的提交和配置。
- 单元测试、集成测试或目标板验证结果。
- 每条偏差的规则编号、位置、理由、替代措施、审批人和复审条件。
- 未运行的工具和未覆盖的模块明确列出。

只有“代码看起来没问题”不构成 MISRA 证据。

## 审查输出建议

把问题分成：

- 阻塞：未定义行为、未初始化、越界、资源泄漏、未检查返回值、明确违反强制规则。
- 需修复：类型转换、控制流、宏副作用、标准库误用。
- 偏差候选：内核惯例与 MISRA 冲突，需要项目批准。
- 证据缺失：版本、配置、工具报告或测试未提供。

不要自行把“无法验证”写成“通过”。
