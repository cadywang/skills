# 内核风格与 MISRA 的冲突处理

## 决策原则

1. 先确认项目是否真的要求 MISRA；Linux 内核本身通常不是 MISRA 合规项目。
2. 项目有正式 MISRA 配置时，安全约束和已批准偏差优先。
3. 没有 MISRA 要求时，按内核风格和子系统惯例执行。
4. 无法判断时标记 `[待确认]`，不要静默选择一种风格。
5. 任何偏差都要写清楚规则、位置、原因、替代措施和审批状态。

## 典型冲突

| 主题 | 内核常见做法 | MISRA 倾向 | 处理方式 |
| --- | --- | --- | --- |
| 单语句花括号 | 通常省略 | 控制流主体使用复合语句 | MISRA 适用时加花括号，即使 `checkpatch` 可能提示冗余 |
| `goto` 清理 | 错误路径常用 `goto err_*` | `goto` 通常受限制或禁止 | 无批准偏差时重构；有偏差时保留并记录 |
| 递归 | 少数场景允许 | 默认禁止递归 | 优先改成迭代、栈或显式队列 |
| 动态内存 | `kmalloc` / `kfree` 常见 | 默认限制分配/释放函数 | 先确认项目规则；不能用则改用静态池或调用方提供缓冲区 |
| 内联汇编 | arch 代码常用 | 通常严格限制 | 隔离在 arch 层，封装 accessor，走偏差 |
| `volatile` | MMIO 和外部变化对象常见 | 对语义有严格限制 | 使用项目 MMIO accessor；不要用 `volatile` 代替锁 |
| union / bitfield | 硬件布局、协议解析中常见 | 类型双关和布局依赖受限制 | 用静态断言、字节访问和文档固定的 ABI；必要时偏差 |
| 函数宏 | 内核大量使用 | 宏副作用和重复求值受限制 | 优先 `static inline`；宏参数加括号并避免副作用 |
| `switch` fallthrough | 某些状态机使用 | 结构完整、受控 fallthrough | 每个分支明确处理；fallthrough 加注释并确认规则允许 |
| 标准库 | 内核通常不用用户态 libc | 受限标准库规则 | 使用内核/项目 API，不把 libc 习惯直接搬进来 |

具体规则编号和适用级别以项目使用的 MISRA 版本为准。

## 花括号示例

MISRA 适用时：

```c
if (condition) {
    do_something();
}
```

不要因为只有一条语句就省略花括号。若项目同时要求内核风格，在提交说明中写明这是 MISRA 约束，不按内核单语句惯例处理。

## `goto` 示例

内核常见写法：

```c
ret = setup();
if (ret)
    goto err_setup;

ret = start();
if (ret)
    goto err_start;

return 0;

err_start:
    stop();
err_setup:
    teardown();
    return ret;
```

如果 MISRA 明确禁止 `goto` 且没有批准偏差，改为：

- 小函数拆分，每层只负责一个资源。
- 调用方提供上下文和清理函数。
- 用显式状态和有限状态机替代跳转。
- 把清理逻辑封装成可复用 helper。

如果保留 `goto` 是 subsystem 的强制模式，记录偏差，不要只写“内核都这么写”。

## 动态内存示例

`kmalloc()` 不是 `<stdlib.h>` 的 `malloc()`，但不能因此自动认为 MISRA 允许。需要确认：

- 项目是否把内核分配器纳入受限 API 清单。
- 分配失败是否有确定处理。
- 生命周期是否有上界。
- 是否允许在中断上下文分配。
- 是否有内存碎片和实时性风险。

安全关键路径优先使用静态分配、调用方缓冲区、内存池或启动时预分配。

## 硬件访问示例

```c
/* 不要用普通 volatile 变量模拟 MMIO 顺序和宽度。 */
value = readl(base + REG_STATUS);
writel(value, base + REG_CONTROL);
```

使用项目提供的 accessor、屏障和位域定义。若硬件布局必须依赖编译器 bitfield 或 union，增加静态断言和 ABI 说明，并评估是否需要 MISRA 偏差。

## 偏差记录模板

```text
规则/条款: <MISRA 版本 + 规则编号>
位置: <file:line 或函数>
代码事实: <为什么不能直接遵守>
风险: <可能后果>
替代措施: <封装、测试、静态断言、运行时检查>
审批: <owner/记录链接；未知则写 [待确认]>
复审条件: <升级工具、重构或下次安全评审时>
```

## 报告方式

- 不要写“完全符合内核风格和 MISRA”，除非两者都有实际检查证据。
- 可以写“已按内核风格修改；MISRA 规则 X 未验证，因为缺少项目配置和分析报告”。
- 偏差候选必须和普通风格问题分开报告。
- 任何未运行的检查都列为 `[待确认]`。
